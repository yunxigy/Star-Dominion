# 守岸人酒馆能力洁净重写路线设计

## 目标

在不引入 SillyTavern AGPL 源码的前提下，为守岸人补齐高级世界书、Persona、Prompt 管理、Character Card V3/CharX、Data Bank/RAG、高级群聊、受限自动化和视觉沉浸能力。

项目采用分阶段交付。每一阶段都必须保持守岸人及全站可启动、可登录、可回归，不等待全部阶段完成后才统一修复问题。

## 许可证与参考边界

守岸人不改为 AGPL，也不复制、改写或迁入 SillyTavern 的源文件、测试、注释和独特文本。

允许使用的参考信息包括：

- 官方公开文档描述的产品行为；
- Character Card 等公开互操作格式；
- 通过守岸人独立测试表达的通用输入与输出行为；
- 许可证与项目策略兼容的第三方库。

本地 `SillyTavern/` 目录仅作为开发期人工参考，不参与守岸人运行、构建、测试或部署。每个新增依赖在引入前检查许可证。最终提交前检查新增代码是否包含与 SillyTavern 高度相同的大段实现、注释或命名结构。

## 总体架构

聊天执行链调整为：

```text
用户消息
  → 会话与角色权限
  → Persona
  → 世界书触发
  → 长期记忆 / RAG
  → Prompt 编排与 Token 预算
  → 模型配置档案
  → LLM
  → 输出后处理
  → 分支、Swipe、记忆与事件记录
```

新增能力拆为六个后端组件：

| 组件 | 职责 | 主要依赖 |
|---|---|---|
| `lorebook_engine` | 计算规则触发、递归、状态、排序和预算 | 世界书模型、Tokenizer |
| `persona_service` | 管理 Persona 及角色/会话绑定 | 用户、角色、会话模型 |
| `prompt_composer` | 编排角色、Persona、世界书、记忆、RAG 和历史 | 上述服务、模型配置档案 |
| `character_card` | 导入导出 V2、V3、CharX 及资源 | 安全上传和资源存储 |
| `knowledge_base` | 文档、切片、Embedding、检索和来源 | 文档存储、向量提供方 |
| `automation_engine` | 快捷动作、事件和白名单指令 | 会话事件、权限服务 |

现有 `server/routers/chat.py` 逐步变成薄路由，仅保留参数解析、鉴权、事务边界和服务调用。现有分支、消息、检查点、备份、TTS/STT、记忆和统一认证继续保留。

## 数据关系

```text
User
├─ Persona
│  ├─ CharacterBinding
│  └─ ChatBinding
├─ KnowledgeBase
│  └─ Document → Chunk → Embedding
└─ AutomationPreset

Character
├─ Lorebook
│  └─ LorebookEntry
├─ CharacterCardRawPayload
└─ CharacterAsset

ChatSession
├─ PersonaBinding
├─ PromptPreset
├─ KnowledgeBinding
├─ LorebookRuntimeState
└─ Existing Branch / Message / Checkpoint
```

新模型使用 SQLAlchemy 和守岸人现有数据库。数据库采用单调递增、可重复执行的增量迁移。现有角色、聊天、世界书和记忆原地保留。

## 第一期：完整世界书执行引擎

第一期让现有世界书字段真正参与聊天，而不是继续只扫描本次输入并按 `priority` 取固定五条。

### 规则能力

- 主关键词和次关键词；
- AND/OR 选择逻辑；
- 普通文本、大小写、整词和正则匹配；
- 常驻条目；
- `before_char`、`after_char` 和指定深度注入；
- 触发概率；
- Sticky、Cooldown 和 Delay；
- 递归触发及最大递归深度；
- 分组互斥、分组权重和确定性优先；
- 角色、Persona 和聊天级绑定；
- Token 预算和溢出裁剪。

世界书状态按会话保存。分支从父分支继承状态；Swipe、删除或恢复检查点后，根据当前有效路径重新计算状态。

引擎返回结构化调试结果，记录每个条目是否命中、未命中原因、递归层级、排序、预算占用和最终注入位置。单条非法规则被隔离并记录，不中断聊天。

## 第二期：Persona 与 Prompt Manager

### Persona

Persona 表示用户在聊天中扮演的身份，包含名称、头像、描述和注入位置。选择顺序为：

1. 会话绑定；
2. 角色绑定；
3. 用户默认 Persona；
4. 无 Persona。

用户可以临时切换 Persona，但临时选择不会覆盖持久绑定。Persona 数据归当前用户所有，不可跨用户读取。

### Prompt Manager

Prompt Manager 将 Prompt 拆成可命名、启停、排序的块，包括：系统规则、角色定义、Persona、世界书、记忆、RAG、Author's Note、历史和最终指令。

预览接口返回块顺序、角色、估算 Token 和裁剪原因。预览永不返回 API Key、内部认证密钥或未授权的管理员配置。

模型配置档案保存 API 类型、模型、生成参数、Prompt 预设和停止词引用。密钥继续由现有站点 AI 配置安全存储，不复制到配置档案。

## 第三期：Character Card V3 与 CharX

角色卡转换层同时保存：

- 守岸人规范化字段，供运行时快速使用；
- 原始兼容载荷，供无损再导出和未来字段升级使用。

支持 V2/V3 的 Scenario、替代开场白、Creator Notes、Post-history Instructions、Character Book、Depth Prompt、Talkativeness、标签和扩展字段。

CharX 资源按清单解包到守岸人角色资源目录。上传处理限制压缩包大小、展开后总大小、文件数量、路径深度和允许的 MIME 类型，并拒绝绝对路径、`..` 路径、符号链接和压缩炸弹。

导入未知字段时保留原始值，不静默删除。导入后再导出的固定样本应保持语义等价；守岸人自身字段写入独立命名空间。

## 第四期：Data Bank 与 RAG

资料库可绑定到用户、角色或会话。首批支持 TXT、Markdown、JSON 和 HTML；PDF 在复用现有文档处理能力后接入。

数据链为：

```text
原始文档 → 解析文本 → 可追踪切片 → Embedding → 检索 → Prompt 引用
```

原文、切片、向量和模型版本分别保存。更换 Embedding 模型时标记旧索引过期并后台重建，不覆盖原文。

生成响应时保存实际使用的片段 ID、来源、相关度和 Token 占用。前端能够展开来源。RAG 不可用时降级为普通聊天，不伪造检索结果或来源。

## 第五期：高级群聊与受限自动化

群聊增加自然、列表、池化和手动发言策略，并支持角色活跃度、禁言、强制发言、自动连续对话、自回复开关和群聊场景覆盖。

自动化系统采用声明式动作，不实现任意 JavaScript、Python、Shell 或模板代码执行。可用动作由后端白名单注册，例如发送预设文本、切换 Persona、切换配置档案、触发指定角色、创建检查点或启停世界书。

自动化支持启动、发送前、回复后、会话打开和世界书触发事件，并限制单次动作数、递归深度、执行时长和调用频率。每次执行写入审计记录。

## 第六期：视觉沉浸与清理

视觉能力按独立资源接口接入：表情立绘、背景、视觉小说布局、动态音频、图像生成和图片理解。AI 能力复用站点现有模型配置和权限，不在守岸人中新增明文密钥。

完成所有能力后才进入参考项目清理。清理不属于普通代码重构，必须单独执行删除前审计和用户确认。

## 安全与权限

- 所有私人资源继续复用统一账号、CSRF 和所有权校验；
- 不存在与无权访问统一返回 404，避免资源枚举；
- Persona、资料库、自动化和运行状态按用户隔离；
- Prompt 预览和调试信息按权限脱敏；
- 上传内容校验 MIME、扩展名、大小、路径和文件数量；
- 自动化无文件系统、Shell、任意网络和任意代码权限；
- 模型密钥不进入聊天备份、角色卡、Prompt 预设或前端状态。

## 降级与错误处理

- 单条世界书规则失败时跳过该条并记录原因；
- Token 超预算时按确定性规则裁剪并返回调试说明；
- Persona 或 Prompt 预设损坏时回退默认配置；
- RAG 或 Embedding 不可用时回退普通聊天；
- 未识别的角色卡字段原样保留；
- 模型请求继续使用现有超时、重试和后端回退；
- 后台重建、文档解析和资源处理失败时保留原始数据，允许重试。

## 测试与验收

每一期包含四层验证：

1. 单元测试：规则、选择顺序、Prompt 编排、格式转换、检索和动作权限；
2. API 测试：登录、CSRF、所有权、非法输入、上传限制和跨用户隔离；
3. 兼容测试：使用项目自制的 V2/V3/CharX 固定样本执行导入—导出；
4. 运行测试：守岸人全量测试、前端脚本语法、整站重启和 `scripts/check-local.ps1`。

每一期的验收条件为：新增行为有回归测试，旧数据可读取，新迁移可重复执行，守岸人及全站冒烟通过，改动单独提交。

## 参考项目清理协议

最终清理前生成候选目录报告，至少检查：

- 启动脚本和服务清单；
- Python/JavaScript import；
- API 代理和反向代理；
- 静态资源和构建输入；
- 配置、数据库和运行路径；
- 文档和部署说明；
- 用户业务数据所在目录。

候选目录分为参考源码、运行服务、构建依赖和用户数据。只允许删除确认无运行引用、无构建引用、无部署依赖且不包含独立业务数据的参考源码。

删除前向用户报告精确绝对路径和原因并取得确认。删除后重新执行全量测试、生产构建、端口检查、统一登录与模块冒烟，并形成保留、移动和删除清单。

## 提交与发布

各阶段在主仓库独立提交。工作区中的其他模块改动不随阶段提交暂存或回退。除非用户明确要求，不自动推送 GitHub。

## 明确不做

- 不复制 SillyTavern AGPL 源码；
- 不让守岸人在运行时依赖 `SillyTavern/`；
- 不一次性推倒现有聊天系统；
- 不开放任意脚本、Shell 或第三方插件执行；
- 不在所有功能完成前删除参考仓库；
- 不未经确认删除任何可能包含用户业务数据的目录。
