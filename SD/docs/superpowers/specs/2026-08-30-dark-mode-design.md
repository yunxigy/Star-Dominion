# 暖棕主题暗色模式设计规范

## 状态

待实现；本规范先提交审阅，确认后再编写实施计划。

## 背景与目标

工具箱目前使用暖米色/棕色视觉系统，页面和工具数量较多，颜色既分布在 `index.css` 的共享类中，也分布在组件里的 Tailwind 固定色类中。暗色模式需要在不破坏现有品牌和工具功能的前提下覆盖整站，并满足用户已确认的行为：

- 首次访问默认跟随操作系统主题。
- 用户可以手动选择“跟随系统、浅色、深色”。
- 手动选择在刷新、路由切换和重新打开页面后保持。
- 操作系统主题变化只影响“跟随系统”状态，不覆盖用户的手动选择。
- 首页、全工具目录、详情页、侧边栏、弹窗和工具内部的界面 chrome 保持一致。

主题切换只改变界面外壳，不改变图片、视频、画布、二维码或其他工具生成内容本身的颜色。

## 范围

### 本批次包含

- 主题偏好状态、持久化和系统主题监听。
- 入口页的无闪烁主题初始化。
- 侧边栏和移动端可访问的主题选择控件。
- 共享背景、玻璃卡片、输入框、目录导航、按钮、统计徽章、空状态、滚动条和详情页外壳的暗色令牌。
- 对现有固定暖色 Tailwind 类的集中兼容映射。
- 单元测试、组件测试和浏览器验收场景。

### 明确不包含

- 分类分页、热度排序、收藏同步或 PWA（按用户确定的 B → C → A 顺序留到后续批次）。
- 新工具、广告、统计、登录和后端接口。
- 对约 211 个工具组件进行一次性颜色重构。
- 对用户上传或生成的媒体做暗色滤镜、反色或色彩增强。

## 方案决策

采用 `data-theme` 属性配合全局语义色令牌，并为少量历史固定色提供兼容映射。

### 方案对比

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| `data-theme` + 语义令牌 + 兼容映射 | 一次覆盖共享布局，改动集中，能渐进消化历史类名 | 需要维护一小组旧类名映射 | **采用** |
| Tailwind `dark:` 逐组件补类名 | 组件意图清晰 | 要修改大量工具页，容易漏改且测试面大 | 不采用 |
| 先全量重构全部颜色再做主题 | 长期最干净 | 范围扩大为整站 UI 重构，交付风险高 | 不采用 |

不启用 Tailwind 的 `dark:` 变体作为主机制；主题的唯一事实来源是 `document.documentElement.dataset.theme`，避免 `class` 和 `data-*` 两套状态漂移。

## 用户体验与交互

### 主题选择

在桌面端侧边栏底部、移动端顶部导航提供同一个主题选择入口。入口显示当前状态，例如“主题：跟随系统”，使用 Sun/Moon 等现有图标库图标，不使用文字符号或自绘图标。

点击后打开一个包含三项的菜单：

1. 跟随系统
2. 浅色
3. 深色

当前选项显示选中状态，选择后立即应用并关闭菜单；焦点回到触发按钮。菜单可用 Tab、方向键和 Enter/Escape 操作，点击菜单外部也会关闭。

### 状态规则

- 存储键固定为 `dream-chaser-theme`，允许值为 `system`、`light`、`dark`。
- 没有存储值、值非法或访问 `localStorage` 失败时，回退到 `system`。
- `system` 通过 `matchMedia('(prefers-color-scheme: dark)')` 解析当前实际主题，并监听后续变化。
- `light` 与 `dark` 直接覆盖系统偏好，不再响应媒体查询变化。
- 路由跳转不重新初始化偏好；刷新后先应用持久化值再渲染 React 树。
- 主题切换可以有极短的颜色过渡；在 `prefers-reduced-motion: reduce` 下关闭过渡。

### 防闪白初始化

`index.tsx` 在创建 React root 之前同步读取偏好并把解析后的主题写到 `document.documentElement`，同时设置 `color-scheme`。组件挂载后只负责订阅变化和更新控件状态，不重复生成两套初始主题。

## 技术结构

### 主题核心

新增一个无 React 依赖的主题模块（建议放在 `lib/theme.ts`），集中负责：

- `ThemePreference` 类型和合法值校验。
- 读取/写入 `localStorage`。
- 根据偏好与 `matchMedia` 解析 `light`/`dark`。
- 应用 `data-theme` 与 `color-scheme`。
- 订阅和清理系统主题变化。

模块必须在 SSR/测试环境没有 `window` 或 `document` 时安全回退，不允许在导入阶段直接访问浏览器全局对象。

### React 控件

新增共享 `ThemeControl`（名称可在实施计划阶段微调），由 `AppLayout` 同时用于桌面侧栏和移动端入口，避免两个控件产生不同状态。控件只调用主题模块的公开接口，不在布局组件内复制媒体查询和存储逻辑。

### CSS 迁移策略

1. 先将 `body`、`.mesh-bg`、`.tool-window-bg`、`.glass-card`、`.glass-sidebar`、`.glass-input`、`.sidebar-item`、统计徽章、空状态和滚动条改为使用语义令牌。
2. 对 `AppLayout`、`PageLayout` 及通用详情壳层中的固定 `text-[#...]`、`bg-[#...]`、`border-[#...]` 做最小替换，优先消除共享入口上的硬编码。
3. 对仍无法立即迁移的历史工具类，只添加明确、可审计的 `[data-theme="dark"]` 兼容规则；不使用全局 `filter`，不覆盖白色文字按钮、品牌彩色图标和媒体内容。
4. 主题规则应集中在 `index.css` 的主题区块，令牌命名和组件级例外写清注释，后续 B2/C/A 批次继续复用。

## 访问性与响应式要求

- 主题入口必须是原生 `button`，有可读的 `aria-label`；菜单有明确的 `role`、选中状态和键盘行为。
- 不能只依靠颜色表达当前主题，选中项同时显示文字和图标/勾选状态。
- 桌面侧栏收缩、移动端顶部导航和触摸尺寸保持现有布局约束，点击区域不小于 44×44 CSS px。
- 暗色下输入框、禁用状态、错误提示、链接和焦点环均需单独检查，不能只检查页面背景。
- 图片、视频、canvas、二维码和用户生成预览不套用暗色滤镜；原生控件如 `<video controls>` 可通过 `color-scheme` 适配浏览器 chrome。

## 测试与验收

### 自动化测试

- `lib/theme.test.ts`：合法/非法存储值、默认 system、系统解析、系统变化监听、`data-theme`/`color-scheme` 应用和清理。
- `components/ThemeControl.test.tsx`：三项菜单、当前选中状态、键盘操作、写入偏好、焦点回归和 `aria` 属性。
- 布局回归测试：`AppLayout` 在桌面和移动入口都挂载同一主题控件，且未引入第二套状态。

### 浏览器验收矩阵

在首页、全工具目录、一个详情页以及至少一个包含图片/视频/canvas 的工具页分别验证：

1. 系统浅色 → 首次打开为浅色；系统深色 → 首次打开为深色。
2. 选择深色/浅色后刷新仍保持，切换路由不丢失。
3. 选择跟随系统后修改系统偏好，页面即时更新；手动模式不随系统变化。
4. 侧栏、移动导航、弹窗、输入框、返回入口和滚动区域没有白块、溢出或文字对比度异常。
5. 工具生成的媒体像素、画布内容和预览颜色没有被主题规则改变。
6. 浏览器控制台无新增错误，键盘可以完整完成打开菜单、选择主题和关闭菜单的流程。

### 项目质量门槛

实现后必须通过现有 `npm.cmd test -- --run --reporter=dot`、`npm.cmd run lint`、`npm.cmd run build`，并保留既有工具注册表校验结果。

## 验收标准

- 用户无需登录即可在桌面和移动端选择三种主题状态。
- 默认行为确实跟随系统，手动选择可持久化且优先级明确。
- 共享页面与详情页的背景、文字、边框、控件和导航在暗色下视觉一致，不出现大块未适配的浅色区域。
- 暗色模式不改变任何图片、视频、canvas 或工具输出内容。
- 主题逻辑有单元/组件测试，关键路径通过浏览器验收，现有测试、lint 和构建保持通过。
- 本批次不引入分页、热度、收藏同步、PWA 或其他 B/C/A 功能。
